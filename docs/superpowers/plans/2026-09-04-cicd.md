# CI/CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Verify every push automatically, and turn deployment into a button that a
server with no inbound route can act on.

**Architecture:** Delivery is inverted because the server sits behind DS-Lite and GitHub
runners cannot reach it. A manual workflow moves a git tag named `production`; a systemd
timer on the server compares that tag against its own state files and, when they differ,
checks the commit out, builds, and restarts. Nothing is ever pushed to the server.

**Tech Stack:** GitHub Actions, bash, systemd, Docker Compose, .NET 8, Angular 17.

**Spec:** `docs/superpowers/specs/2026-09-04-cicd-design.md`

## Global Constraints

- Deploy tag name: `production`. The agent reads no other ref.
- App directory on the server: `/srv/wedding/app`
- State files, outside the repository: `/srv/wedding/deployed-commit`,
  `/srv/wedding/failed-commit`
- Installed script path: `/usr/local/bin/wedding-deploy`
- Unit name: `wedding-deploy` (`.service` and `.timer`)
- Poll interval: 2 minutes
- No secrets are created anywhere. The deploy workflow uses the built-in `GITHUB_TOKEN`.
- `docker compose build` must run before `up -d`, never after.
- The agent must never run `git clean`. The server's `.env` lives in the app directory.
- Workflow inputs must reach shell commands through `env:`, never through `${{ }}`
  interpolated directly into a `run:` block.
- Documentation in `docs/DEPLOYMENT.md` is written in Polish; specs and plans in English.

## File Structure

| File | Responsibility |
| --- | --- |
| `.github/workflows/ci.yml` | Verify backend, frontend and container images on every push and PR. Touches nothing outside the runner. |
| `.github/workflows/deploy.yml` | The button. Resolves a ref to a commit and force-moves the `production` tag. Nothing else. |
| `deploy/wedding-deploy.sh` | The whole convergence algorithm: fetch, decide, checkout, build, start, record. |
| `deploy/wedding-deploy.service` | `Type=oneshot` unit invoking the installed script. |
| `deploy/wedding-deploy.timer` | Fires the unit every two minutes. |
| `deploy/test-wedding-deploy.sh` | Runs the agent against a scratch repository with a stub `docker`, covering the five decision paths. |
| `docs/DEPLOYMENT.md` | Gains a section on installing the agent, deploying, rolling back, and clearing a failed deploy. |

## Task 1: CI workflow

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: nothing.
- Produces: nothing other tasks depend on. This task is deliberately standalone so it can
  land and be useful before any deployment machinery exists.

- [ ] **Step 1: Write the workflow**

Create `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      - name: Build
        run: dotnet build WeddingGallery.sln -c Release

      - name: Test
        run: dotnet test WeddingGallery.sln -c Release --no-build --verbosity normal

  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm
          cache-dependency-path: ClientApp/package-lock.json

      - name: Install
        run: npm ci
        working-directory: ClientApp

      - name: Build
        run: npm run build
        working-directory: ClientApp

  images:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # The server compiles for itself, so a broken Dockerfile would otherwise pass CI and
      # fail on production after the tag has already moved. Building here moves that
      # failure to before the button.
      - name: Write placeholder environment
        run: |
          cat > ci.env <<'EOF'
          POSTGRES_DB=ci
          POSTGRES_USER=ci
          POSTGRES_PASSWORD=ci
          DATA_ROOT=./ci-data
          ADMIN_PASSWORD=ci
          ADMIN_TOKEN=ci
          DOMAIN=ci.invalid
          CLOUDFLARE_TUNNEL_TOKEN=ci
          EOF

      # docker-compose.yml interpolates ${DOMAIN:?...} and friends, so Compose refuses to
      # read the file at all without them. These values grant nothing and are not secrets;
      # they exist only to satisfy interpolation.
      - name: Build images
        run: docker compose --env-file ci.env build
```

## Task 2: The deploy agent

**Files:**
- Create: `deploy/wedding-deploy.sh`
- Create: `deploy/wedding-deploy.service`
- Create: `deploy/wedding-deploy.timer`
- Test: `deploy/test-wedding-deploy.sh`

**Interfaces:**
- Consumes: a git tag named `production` on the origin remote. Task 3 creates it for real;
  this task fakes one, so the two are independent.
- Produces: the contract Task 4 documents. Script installed at `/usr/local/bin/wedding-deploy`;
  state in `/srv/wedding/deployed-commit` and `/srv/wedding/failed-commit`; three
  environment overrides exist purely so the test can redirect it: `APP_DIR`, `DEPLOY_TAG`,
  `STATE_DIR`.

- [ ] **Step 1: Write the failing test**

Create `deploy/test-wedding-deploy.sh`. It builds a scratch origin and clone, puts a stub
`docker` on `PATH` that records its arguments and can be told to fail, then drives the
agent through every decision path. No Docker and no server are involved.

```bash
#!/usr/bin/env bash
# Exercises deploy/wedding-deploy.sh against a scratch repository.
set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
AGENT="$SCRIPT_DIR/wedding-deploy.sh"
WORK="$(mktemp -d)"
trap 'rm -rf "$WORK"' EXIT

failures=0
check() {
  if [ "$2" = "$3" ]; then echo "OK    $1"; else
    echo "FAIL  $1"; echo "        expected: $3"; echo "        actual:   $2"
    failures=$((failures + 1))
  fi
}

export GIT_AUTHOR_NAME=test GIT_AUTHOR_EMAIL=test@test
export GIT_COMMITTER_NAME=test GIT_COMMITTER_EMAIL=test@test

git init -q --bare "$WORK/origin.git"
git clone -q "$WORK/origin.git" "$WORK/app" 2>/dev/null
cd "$WORK/app"
echo one > file.txt && git add . && git commit -qm one
first="$(git rev-parse HEAD)"
echo two > file.txt && git commit -qam two
second="$(git rev-parse HEAD)"
git push -q origin HEAD:master

# Stub docker: records every invocation, and fails when FAIL_ON matches the subcommand.
mkdir -p "$WORK/bin"
cat > "$WORK/bin/docker" <<'STUB'
#!/usr/bin/env bash
echo "$*" >> "$DOCKER_LOG"
if [ -n "${FAIL_ON:-}" ] && [ "${2:-}" = "$FAIL_ON" ]; then exit 1; fi
exit 0
STUB
chmod +x "$WORK/bin/docker"
export PATH="$WORK/bin:$PATH"

STATE="$WORK/state"
mkdir -p "$STATE"
run_agent() {
  DOCKER_LOG="$WORK/docker.log" APP_DIR="$WORK/app" STATE_DIR="$STATE" \
    DEPLOY_TAG=production bash "$AGENT" > "$WORK/out.txt" 2>&1
  echo $?
}
tag_at() { git -C "$WORK/app" tag -f production "$1" -m x 2>/dev/null || git -C "$WORK/app" tag -f production "$1"; git -C "$WORK/app" push -q --force origin refs/tags/production; }

# 1. No tag at all: quiet success, nothing built.
: > "$WORK/docker.log"
check "no tag exits 0" "$(run_agent)" "0"
check "no tag builds nothing" "$(wc -l < "$WORK/docker.log" | tr -d ' ')" "0"

# 2. Tag moved: checkout, build, up, state recorded.
tag_at "$first"
: > "$WORK/docker.log"
check "deploy exits 0" "$(run_agent)" "0"
check "deploy built" "$(grep -c 'compose build' "$WORK/docker.log")" "1"
check "deploy started" "$(grep -c 'compose up -d' "$WORK/docker.log")" "1"
check "build precedes up" \
  "$(grep -n 'compose build\|compose up' "$WORK/docker.log" | head -1 | grep -c build)" "1"
check "records deployed commit" "$(cat "$STATE/deployed-commit")" "$first"
check "checked out the commit" "$(git -C "$WORK/app" rev-parse HEAD)" "$first"

# 3. Same tag again: nothing happens.
: > "$WORK/docker.log"
check "already deployed exits 0" "$(run_agent)" "0"
check "already deployed does nothing" "$(wc -l < "$WORK/docker.log" | tr -d ' ')" "0"

# 4. Build fails: non-zero, failure recorded, containers left alone.
tag_at "$second"
: > "$WORK/docker.log"
FAIL_ON=build
export FAIL_ON
check "failed build exits non-zero" "$(run_agent)" "1"
check "failed build never starts containers" "$(grep -c 'compose up' "$WORK/docker.log")" "0"
check "records failed commit" "$(cat "$STATE/failed-commit")" "$second"
check "deployed commit unchanged" "$(cat "$STATE/deployed-commit")" "$first"

# 5. Same failed commit next tick: skipped, not retried.
: > "$WORK/docker.log"
check "known failure exits 0" "$(run_agent)" "0"
check "known failure does not rebuild" "$(wc -l < "$WORK/docker.log" | tr -d ' ')" "0"
unset FAIL_ON

echo
[ "$failures" -eq 0 ] && echo "ALL PASS" || echo "$failures FAILURES"
exit $((failures == 0 ? 0 : 1))
```

- [ ] **Step 3: Write the agent**

Create `deploy/wedding-deploy.sh`:

```bash
#!/usr/bin/env bash
# Converges the checked-out application onto whatever commit the `production` tag names.
#
# Delivery is pull-based because the server sits behind DS-Lite and nothing can reach it
# from outside. This script is the only thing that decides what runs.
set -uo pipefail

APP_DIR="${APP_DIR:-/srv/wedding/app}"
STATE_DIR="${STATE_DIR:-/srv/wedding}"
DEPLOY_TAG="${DEPLOY_TAG:-production}"

DEPLOYED_FILE="$STATE_DIR/deployed-commit"
FAILED_FILE="$STATE_DIR/failed-commit"

cd "$APP_DIR" || { echo "No app directory at $APP_DIR"; exit 1; }

git fetch --tags --force --prune origin || { echo "Fetch failed"; exit 1; }

if ! git rev-parse --verify --quiet "refs/tags/${DEPLOY_TAG}^{commit}" > /dev/null; then
  echo "No ${DEPLOY_TAG} tag yet; nothing to deploy."
  exit 0
fi

target="$(git rev-parse "refs/tags/${DEPLOY_TAG}^{commit}")"
deployed="$(cat "$DEPLOYED_FILE" 2>/dev/null || true)"
failed="$(cat "$FAILED_FILE" 2>/dev/null || true)"

if [ "$target" = "$deployed" ]; then
  exit 0
fi

# One attempt per tag move. A broken commit must not rebuild every two minutes forever.
# Move the tag again, or delete this file, to retry.
if [ "$target" = "$failed" ]; then
  echo "${target} already failed; skipping. Delete ${FAILED_FILE} to retry."
  exit 0
fi

echo "Deploying ${target} (was ${deployed:-unknown})"

# --force discards local edits to tracked files, which would otherwise wedge every future
# deploy. Untracked and ignored files are untouched, so the server's .env is safe. There is
# deliberately no `git clean` anywhere in this script.
if ! git checkout --detach --force "$target"; then
  echo "Checkout failed"
  mkdir -p "$STATE_DIR" && echo "$target" > "$FAILED_FILE"
  exit 1
fi

# build leaves the running containers alone, so a failure here changes nothing that is
# currently serving. Only once it succeeds do we restart anything.
if ! docker compose build; then
  echo "Build failed; leaving the running containers alone."
  mkdir -p "$STATE_DIR" && echo "$target" > "$FAILED_FILE"
  exit 1
fi

if ! docker compose up -d; then
  echo "Start failed."
  mkdir -p "$STATE_DIR" && echo "$target" > "$FAILED_FILE"
  exit 1
fi

mkdir -p "$STATE_DIR"
echo "$target" > "$DEPLOYED_FILE"
rm -f "$FAILED_FILE"
echo "Deployed ${target}."
```

- [ ] **Step 4: Run the test until it passes**

```bash
bash deploy/test-wedding-deploy.sh
```

Expected: `ALL PASS`, exit code 0. Every check must pass, in particular "build precedes up"
and "failed build never starts containers" - those two encode the whole reason the build
and start steps are separate.

- [ ] **Step 5: Write the systemd units**

Create `deploy/wedding-deploy.service`:

```ini
[Unit]
Description=Converge Wedding Gallery onto the production tag
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
# Installed copy, not the one in the working tree: running it in place would have the
# script executing a file its own git checkout is replacing underneath it.
ExecStart=/usr/local/bin/wedding-deploy
```

Create `deploy/wedding-deploy.timer`:

```ini
[Unit]
Description=Check every two minutes for a new Wedding Gallery deployment

[Timer]
OnBootSec=2min
OnUnitActiveSec=2min
Unit=wedding-deploy.service

[Install]
WantedBy=timers.target
```

A build can outlast the interval. `OnUnitActiveSec` measures from the last activation and
systemd will not start a unit that is still running, so runs cannot overlap.

```

## Task 3: The deploy button

**Files:**
- Create: `.github/workflows/deploy.yml`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: a force-moved git tag named `production` on the origin remote. This is the
  single value Task 2's agent reads.

- [ ] **Step 1: Write the workflow**

Create `.github/workflows/deploy.yml`:

```yaml
name: Deploy

# The server is behind DS-Lite and cannot be reached from here. This workflow does not
# deploy anything itself: it moves the `production` tag, and the agent on the server
# converges onto it within two minutes.
on:
  workflow_dispatch:
    inputs:
      ref:
        description: 'Commit SHA, branch or tag to deploy'
        required: true
        default: master

permissions:
  contents: write

jobs:
  move-tag:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      # The input reaches the shell through env, never through ${{ }} inside run:.
      # Interpolating it directly would let the value inject shell commands.
      - name: Resolve the ref to a commit
        id: resolve
        env:
          REF: ${{ inputs.ref }}
        run: |
          sha="$(git rev-parse "${REF}^{commit}")"
          echo "sha=${sha}" >> "$GITHUB_OUTPUT"
          echo "Deploying ${sha} (from ${REF})"

      - name: Move the production tag
        env:
          SHA: ${{ steps.resolve.outputs.sha }}
        run: |
          git config user.name 'github-actions[bot]'
          git config user.email 'github-actions[bot]@users.noreply.github.com'
          git tag --force production "${SHA}"
          git push --force origin refs/tags/production
          echo "production now points at ${SHA}"
```

```markdown
## 11. Automatyczne wdrożenia (CI/CD)

Serwer jest za DS-Lite, więc GitHub nie ma jak się do niego połączyć. Wdrożenie jest
odwrócone: przycisk w GitHubie przestawia tag `production`, a timer na serwerze co dwie
minuty sam się do niego zbiega.

### Instalacja agenta (jednorazowa)

```bash
cd /srv/wedding/app
sudo install -m 755 deploy/wedding-deploy.sh /usr/local/bin/wedding-deploy
sudo install -m 644 deploy/wedding-deploy.service /etc/systemd/system/
sudo install -m 644 deploy/wedding-deploy.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now wedding-deploy.timer
```

Skrypt i pliki jednostek są **kopiowane** z repozytorium. Zmiana któregokolwiek z nich
wymaga powtórzenia tych komend — agent nie aktualizuje się sam, bo nie może wykonywać
pliku, który jego własny `git checkout` podmienia mu pod nogami.

### Wdrożenie

Actions → Deploy → Run workflow → podaj commit, gałąź lub tag (domyślnie `master`).
W ciągu dwóch minut serwer się przełączy.

### Cofnięcie

Ten sam przycisk ze starszym SHA. To jedyny mechanizm — nie ma osobnej procedury awaryjnej.

### Co się dzieje i czy się udało

```bash
systemctl status wedding-deploy.timer
journalctl -u wedding-deploy -n 50 --no-pager
cat /srv/wedding/deployed-commit
```

**Przycisk w GitHubie zapala się na zielono, gdy tag się przestawi — nie gdy wdrożenie
się uda.** Prawda jest tylko w journalu.

### Nieudane wdrożenie

Agent próbuje **raz na przestawienie tagu**. Po porażce zapisuje commit i przestaje,
żeby nie przebudowywać co dwie minuty w kółko:

```bash
cat /srv/wedding/failed-commit
```

Ponowna próba tego samego commita:

```bash
sudo rm /srv/wedding/failed-commit
```

Nieudany `build` **nie rusza działających kontenerów** — galeria dalej chodzi na starym
kodzie. Nieudany `up -d` już tak, i wtedy trzeba zajrzeć od razu.

### Ręczne wdrożenie (awaryjnie)

Gdy agent nie działa:

```bash
cd /srv/wedding/app
git fetch --tags --force origin
git checkout --detach --force production
docker compose build && docker compose up -d
```
```

## After the plan

The agent has never run on the real server, and nothing in this plan can change that.
Installing it and watching the first convergence is a manual step, and until it happens the
deploy button is a tag-mover with nothing listening.

The first real deploy is therefore: install the agent, press the button, and read
`journalctl -u wedding-deploy`.
